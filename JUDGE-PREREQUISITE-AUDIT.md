# Judge integration prerequisite audit

Date: 2026-10-30

## Outcome

Judge runtime integration was stopped at the handoff's prerequisite gate. The provider and Paksh files exist and their current tests pass, but the engine does not expose the shared repair allowance that the handoff explicitly requires the Judge to reuse. Cancellation and unknown-usage accounting also need completion before relying on them across hearing stages. No Judge preview or live Judge is delivered.

The supplied judge-adjudicator-skill-v1.0.zip was extracted to skills/judge-adjudicator without altering its policy, schemas, examples, or reference utilities. The Paksh package is already present at skills/paksh-advocate.

## Existing architecture mapping

- Providers: server/providers/index.mjs getAdapter(providerId, options), with generate() implementations in the individual provider modules.
- Connections and per-role assignments: server/connections.mjs ConnectionManager; server-memory storage.
- Local security: server.mjs validateHost and server/routes.mjs session-token and request-size checks.
- Engine: server/engine/{schema,context,json-reply,request-log,orchestrator}.mjs.
- Quote occurrence and merge: server/engine/{verify-quotes,merge-ledgers}.mjs.
- Real Paksh opening: server/engine/roles/paksh.mjs runOpening; orchestration through runHearingPakshOpening.

## Missing prerequisite capabilities

1. **Shared repair allowance.** server/engine/roles/paksh.mjs initializes `retries = 0` inside runOpening and unconditionally permits its own repair. Neither the hearing state nor role dependencies expose a shared repair counter/consumer. A later Judge cannot reuse the existing initiating-action allowance as requested. This is the direct integration blocker; file presence alone does not satisfy that contract.
2. **Conservative unknown-usage accounting.** Paksh only calls recordUsage when total usage is known. The orchestrator checks tokensUsed plus an estimate but retains no reservation for a completed call with unknown usage. Such work is effectively absent from subsequent budget checks. The Judge's branch reservations are new task work, but the existing Paksh call must first participate in common accounting.
3. **Late-result cancellation guard.** The orchestrator aborts a controller on deletion, but after runOpening resolves it writes the opening without checking cancellation, hearing membership, or a run generation. The role checks cancellation in exception paths only. A provider that resolves after abort can still produce an accepted successful result on the retained hearing object. Generation-aware acceptance is needed before reusing cancellation across stages.

These findings were established by source inspection, not by newly added regression tests. No prerequisite implementation was rebuilt in this task.

## Separate full-live limitation

There is no genuine Vipaksh runOpening/runClarify adapter. server/engine/roles/scripted.mjs returns a supplied statement with empty claims and no model calls. Paksh exports runOpening only; its hearing-specific clarification adapter is also absent. The handoff assigns that new clarification adapter to Judge integration, so its absence is not independently treated as a prerequisite-gate failure. Vipaksh is not a prerequisite for a future fixture-backed preview, but full live hearing and automatic continuation must remain unavailable until real side adapters exist.
